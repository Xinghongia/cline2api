# 2026-09-25 M3：成熟用量统计——SQLite 地基、用量归因修复、API Key 对象化

## 背景

旧实现的用量统计有三个根本缺陷：①请求日志是 JSON 文件（上限 5000 条/30 天），无时间聚合，无法支撑"成熟统计"；②zen 与 provider 路径的用量归因缺失（错误路径甚至不落日志）；③API Key 是无元数据的纯字符串，无法按 Key 统计。M3 用 SQLite 重建存储地基，并补齐归因链路。

## 改动范围

### 存储层（internal/reqlog 整体重写）

- 引入 `modernc.org/sqlite v1.59.0`（纯 Go，CGO_ENABLED=0 不影响 Docker/桌面交叉编译）
- `usage.db` 双表：
  - `request_logs`：原始记录，扩列 `api_key_id` / `provider_id` / `error_class`，索引 started_at/model/api_key_id
  - `usage_hourly`：小时聚合桶，主键 (bucket, model, upstream, api_key_id)，写入时 UPSERT 累加
- 保留策略：原始日志 90 天、小时桶 1 年；启动 + 每小时清扫（sweep）
- WAL 模式 + `MaxOpenConns(1)` 串行化写入：个人规模足够，杜绝 SQLITE_BUSY
- 写路径：`AppendRequestLog` = 一个事务内 INSERT 原始记录 + UPSERT 聚合桶
- 读路径新增：`SeriesQuery`（hour|day 桶 × total|model|upstream|key 分组）、`SummaryQuery`（总量 + 模型 Top + 上游分布 + Key Top）、`SumUpstream`（zen 今日卡片）、`KeyUsage`
- `FinalizeRequestLog` 增加错误分类：rate_limit / auth / timeout / network / upstream / client / other（关键词粗分，够用且零成本）
- 旧 `.cline-request-logs.json` 封存不迁移（残留数据价值低，避免复杂迁移逻辑）

### 用量归因修复（internal/server）

- **API Key 归因**：鉴权中间件匹配成功后把 key 写入 request context；三个协议处理器（chat/messages/responses）创建 reqLog 时取回 `APIKeyID`
- **Provider 归因**：`callClineAPI`/`callCustomProviderAPI` 显式接收 `rl *types.RequestLog`，provider 命中时写 `rl.ProviderID = p.ID`
- **错误路径漏日志**（本次实测发现的真 bug）：`"No accounts in pool"` 401 提前返回不落日志（chat 与 anthropic 两处）→ 补 `FinalizeRequestLog`；之前 zen 请求失败时日志完全丢失
- 测试调用点兼容：`callClineAPI(params, false)` → `callClineAPI(params, false, nil)`

### API Key 对象化

- `types.APIKey`：key/name/enabled/createdAt/lastUsedAt/totalRequests
- **向后兼容迁移**：`UnmarshalJSON` 接受旧版纯字符串（自动 Enabled=true）或新对象格式；`.cline-accounts.json` 无需手工迁移
- 鉴权语义增强：禁用的 Key（enabled=false）返回 401
- 使用即记账：LastUsedAt/TotalRequests 更新并立即落盘
- 新端点 `POST /admin/api/keys/update`（改名/启停）；`GET /admin/api/keys` 响应合并 SQL 聚合出的单 Key Token 用量

### 新端点（internal/server/admin.go）

- `GET /admin/api/stats/series`：bucket=hour|day、group=total|model|upstream|key、from/to（Unix 秒）+ 筛选
- `GET /admin/api/stats/summary`：range=24h|7d|30d，返回 totals/topModels/upstreams/topKeys
- `GET /admin/api/request-logs`：新增 model/upstream/key/status/q/从到筛选（SQL WHERE 拼接）

### 前端

- `components/Chart.tsx`：ECharts 按需注册（echarts/core + Line/Bar/Pie），跟随容器 resize、暗色模式取色
- Dashboard：24h/7d/30d 切换、用量趋势双轴图（请求柱状 + Token 折线）、上游分布环形图、模型 Top5 横向条形图
- Logs：筛选栏（模型/上游/结果/搜索）+ Key 列
- Keys：对象化表格（名称可编辑、启停开关、用量四项、最近使用），生成时可填名称
- en.json 补 17 个词条

## 关键决策

1. **reqlog 保留包级函数 API**（AppendRequestLog 等），内部换成全局 Store + `G()` 懒初始化——server/zen 调用方零改动。
2. **测试隔离弃用 ":memory:"**：modernc 驱动下多次打开内存库发生**数据串库**（不同测试看到彼此数据，且 `?mode=memory&cache=shared` 唯一命名也不隔离）。改为独立临时文件库 + Close 删除，确定性隔离。
3. **归因参数显式传递而非 context 透传到深层**：provider 命中点在 callCustomProviderAPI 内部（ResolveProviderForModel 之后），只有显式传 `rl` 才能精确归因；测试调用点用 nil 填充。
4. **Key 的 Token 用量不入 Key 对象**：从 usage_hourly 聚合查询，单一事实来源（日志），避免双记账漂移；Key 对象只存 LastUsedAt/TotalRequests 这类高频轻量计数。

## 踩坑与修复

1. **modernc 内存库串库**（见决策 2）——症状是测试间数据累积（Len=8），根因是连接池重建连接后 `:memory:` 每连接独立，shared cache 又不按预期隔离；临时文件方案彻底解决。
2. **go mod tidy 误删依赖**：`go get modernc.org/sqlite` 后若 tidy 在代码引用前执行会移除它；先写代码再 tidy。
3. **"No accounts in pool" 日志缺失**（本里程碑最大的收获）：是探索阶段标记的"zen/provider 用量丢弃"之外漏掉的第三个归因缺口——错误路径的 401 从不落日志。实测驱动发现（发请求 → 查日志为空 → 顺藤摸瓜）。
4. **zen 故障转移影响测试观察**：zen 上游 401 后状态机进入故障转移窗口，后续 zen 模型请求被重写到 cline 路径（`zen failover: rewriting zen model`）——这是设计行为，验证时需注意。

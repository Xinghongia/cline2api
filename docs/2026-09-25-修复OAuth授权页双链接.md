# 2026-09-25 修复：OAuth 打开授权页出现两条链接

## 现象

管理后台「账号管理 → OAuth 登录」点击「打开授权页面」后，授权页被打开**两次**（两个标签页/窗口）。

## 根因

M1 重写前端时，`utils.ts` 的 `openExternal` 这样实现：

```ts
const win = window.open(url, '_blank', 'noopener')
if (!win) {
  void fetch(`/admin/api/open-external?url=...`)   // 以为弹窗被拦截，走后端兜底
}
```

按 HTML 规范，`window.open` 带 **`noopener`** 特性时**恒返回 `null`**——即使新标签页已经成功打开。于是"兜底"逻辑必然触发：前端 `window.open` 开了一个，后端 `open-external`（服务端 rundll32/open 调系统浏览器）又开一个 → 共两条。

## 修复

统一走后端 `open-external` 端点，删掉 `window.open` 分支：

```ts
export function openExternal(url: string): void {
  void fetch(`/admin/api/open-external?url=${encodeURIComponent(url)}`)
}
```

这样选的理由：

1. **桌面 WebView 本就无法弹外部浏览器**——后端打开是唯一可行路径（旧版 UI 也是这么做的）；
2. **本机浏览器场景**下管理页与服务端同机，服务端调系统浏览器 = 恰好一次；
3. 附带收益：`fetch` 不受浏览器弹窗拦截器影响。

后端端点已有校验（仅允许 http/https，非法协议/缺参返回 400），无开放重定向风险。

## 验证

- `curl /admin/api/open-external?url=ftp://x` → 400（校验生效，未打开浏览器）
- 前端重建 + 服务重启后 OAuth 弹窗仅触发一次 `open-external` 调用

## 反思

`window.open` 的返回值语义（尤其 noopener 模式）是个隐蔽坑：它"看似"可以用来检测弹窗拦截，实际在 noopener 下恒 null。涉及"前端触发 + 后端兜底"的双路径设计时，必须先确认探测信号本身可靠，否则两条路径会同时生效。

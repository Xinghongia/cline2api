# 2026-09-25 M4：通用提供商——Anthropic 协议适配与直连路由，中转站成型

## 背景

M4 之前，自定义 provider 有两个结构性限制：①只支持 OpenAI 兼容协议（`callProvider` 硬编码 `/chat/completions`）；②路由上被困在 cline 分支内（`callClineAPI` 内部先试 provider），命中 zen 的模型永远到不了 provider，`/v1/models` 也不暴露 provider 模型。M4 把 provider 升级为一等公民，实现"上游任意格式、下游统一出口"的中转站能力。

## 改动范围

### internal/providers

- `CustomProvider` 新增 `protocol`（"openai"|"anthropic"，空按 openai）与 `modelMapping`（暴露 ID → 上游真实 ID，缺省同名直传）
- `EffectiveProtocol()` / `UpstreamModelFor(exposed)` 方法（值接收者，便于测试字面量直接调用）
- 预设表新增 `anthropic`（Anthropic 官方）与 `claude-relay`（任意 anthropic 协议中转），`ProviderPreset` 增加 `Protocol` 字段

### internal/server/anthropic_upstream.go（新增，Anthropic 协议边界层）

三种转换，使 provider 执行边界对上层完全透明：

1. `openAIParamsToAnthropicBody`：请求体转换——system 消息上提为顶层 `system`；`tool` 角色转 `user` + `tool_result` 块；assistant `tool_calls` 转 `tool_use` 块（arguments 字符串 → input 对象）；tools 定义 `parameters` → `input_schema`；`max_tokens` 为 Anthropic 必填（默认 8192）
2. `anthropicMessageToOpenAI`：非流式响应转换——content blocks 聚合为 text + tool_calls；`stop_reason` 映射（end_turn/stop_sequence→stop、max_tokens→length、tool_use→tool_calls）；usage 三项换算
3. `anthropicStreamToOpenAIStream`：SSE 流实时转写——`text_delta` → `delta.content`；`input_json_delta` → `tool_calls[].function.arguments` 增量（带 index 对齐）；`message_delta` 的 usage/stop_reason 归入收尾块；`message_stop` 后补 `[DONE]`；上游断流时补发收尾块避免客户端悬挂

### 路由升级（internal/server）

- `tryProvider(params, stream, rl)` 中转站核心路径：模型命中启用 provider → 直连（`Upstream="provider"`、`ProviderID` 归因），失败自动降级 zen/cline 常规路由
- 三个处理器（chat/messages/responses）在 `RouteModel` 之前先走 `tryProvider`——provider 优先级高于一切，且三种客户端协议都能命中
- `callProvider` 协议分支：anthropic 上游 POST `BaseURL + /v1/messages`（`x-api-key` + `anthropic-version` 头），成功响应统一转写为 OpenAI 形态（流式包一层转写 Reader，非流式转换 JSON）——下游 handleStream/handleNonStream/handleAnthropicStream 零改动
- 模型映射在 callProvider 内统一应用（两种协议同一路径）
- `getAllModels` → `withProviderModels(result)`：启用 provider 的模型并入模型列表（去重），`Source="provider"`，`/v1/models` 与后台模型页同步可见

### 前端

- Provider 编辑器：上游协议选择器（OpenAI 兼容 / Anthropic）、模型映射编辑器（对外 ID → 上游真实 ID 行编辑，保存时合并为 `modelMapping` 对象）
- 提供商列表增加协议徽标（anthropic 紫 / openai 蓝）；预设应用自动带出协议
- en.json 补 6 个词条

## 关键决策

1. **转换边界放在 callProvider，而非各客户端协议处**：内部规范形态始终是 OpenAI chat 参数/响应。若按"客户端协议 × 上游协议"做 3×2 转换矩阵，SSE 处理会爆炸；收敛到"上游协议 → OpenAI"单一边界后， anthropic 客户端打到 anthropic 上游 = 双层转换自动串联（anthropic client → openai 内部 → anthropic 上游 → openai 内部 → anthropic client），实测通过。
2. **provider 优先级高于 zen**：直连检查放在 handler 层 `RouteModel` 之前，"reject"（zen 付费拒绝）也会被 provider 覆盖——provider 是管理员显式配置的，应压过内置路由规则。失败降级而非报错，保持"尽力服务"语义。
3. **测试调用点零破坏**：`tryProvider` 只在 handler 层调用，`callClineAPI` 内部的 provider 兜底保留（双重保险），不改变已有测试语义。

## 踩坑与修复

1. **chunkEmitter 忘挂 writer**：`e := &chunkEmitter{...}` 少了 `w: pw`，goroutine 里 `fmt.Fprintf(nil)` 空指针 panic。教训：结构体字面量字段多时（3 个以上）尤其容易漏，go vet 不报、测试一跑就现形。
2. **值接收者 vs 指针接收者**：测试里 `(CustomProvider{}).EffectiveProtocol()` 编译失败（指针接收者方法不能被不可寻址字面量调用）。这两个方法本就无 mutation，改为值接收者。
3. **`[]any{{...}}` 嵌套字面量**：any 元素的复合字面量不能省略类型，需写全 `[]any{map[string]any{...}}`。
